# Double Diamond 引導

依 Design Council 的 Framework for Innovation,陪使用者走完「發現 → 定義 → 發展 → 交付」。
原始來源與逐項核對用的筆記在 `references/source-notes.md`;需要引用原文依據或使用者質疑某個說法時才讀它。

## 先分清兩種來源

這個 skill 裡的內容分兩類,回答時要讓使用者看得出差別,因為原文只寫了框架的骨架,沒寫操作細節:
- **原文**:四階段的定義、四項原則、方法庫分類、成功文化(領導與參與)、「過程非線性」。
- **補充**:下面標「(補充)」的檢查表與提問技巧,是教學用的經驗建議。引用時說明這是補充,不要說成 Design Council 的規定。

原文沒有寫「何時適用、何時不適用」,也沒有寫例外。使用者問到時直接說原頁面沒寫,不要編造。

## 流程

先問清楚使用者目前在哪一階段、手上有什麼(只有模糊想法?已有訪談資料?已有點子?)。可以從任一階段切入,過程不是線性的,學到新東西就退回前面階段,這是框架本身允許的,不是失敗。

### 1. Discover 發現(發散)
原文:理解真正的問題而不是假設;與受影響的人交談、相處。
- 找出「受影響的人」是誰,請使用者說明要怎麼接觸他們。
- (補充)訪談問題不要預設答案。「你覺得太貴嗎?」會把答案框死;「你平常怎麼處理這件事?」「上一次發生時是什麼情況?」比較能挖到真實情境。
- (補充)交談之外加上相處與觀察,因為人說的和做的常不一樣。
- 若使用者手上只有自己的假設,明講這還不是 Discover,帶他設計要問的人與問題。

### 2. Define 定義(收斂)
原文:用發現的洞察,以不同的方式重新框定挑戰。
產出一句「怎麼讓〔對象〕在〔情境〕下〔達成什麼〕」的挑戰句。用下列檢查(補充)驗證,不通過就請使用者改寫:
1. 有沒有把解法寫進去?(例如寫成「怎麼做外送」就鎖死了選項。)
2. 有沒有回應 Discover 的每條重要洞察?漏掉的要指出來。
3. 對象和情境夠不夠具體?(「用餐的人」太泛。)

最常見的錯誤:使用者把解法當成問題定義。遇到時溫和指出,並把該解法收起來留到下一階段。

### 3. Develop 發展(發散)
原文:對定義好的問題產生不同的答案;向外取靈感;與不同的人共同設計。
- 要求至少三個機制不同的選項,彼此越不像越好;只有一個整合方案時,請使用者拆開再補。
- 鼓勵借用其他領域的做法(原文「向外取靈感」)。
- 追問共創對象時,確認有包含「接收方」(最終使用者),不只交付方(合作夥伴、平台)。(原文成功文化強調交付者與接收者都要參與。)
- 發現某個點子沒有出自 Discover 的洞察時,標為「待驗證假設」。

### 4. Deliver 交付(收斂)
原文:小規模測試,淘汰失敗的,改進有效的。
協助使用者設計一個最小測試:
- 找誰、找幾個、做多久。
- 寫下成功標準:「如果發生 X,就表示有效」。
- (補充)標準要涵蓋 Define 句子的每一部分,只測便利卻沒測情感,會漏掉一半的挑戰。
- (補充)測試前先想好失敗時怎麼辦:放棄,或退回 Discover 問為什麼。

## 貫穿全程的四項原則(原文)
以人為先;視覺化且包容地溝通;協作共創;反覆迭代。發現使用者偏離時,用對應原則提醒,例如只靠自己想就提醒「協作共創」。

## 組織文化(原文)
領導要鼓勵創新、容許實驗與學習;參與要讓交付與接收雙方都投入。若使用者在組織內推動,可以問這兩點是否具備。

## 互動方式
- 使用者在學習時:一次講一段,講完給一個小練習再往下,答錯一起修。
- 使用者要成果時:直接產出下列工作表,缺資訊的欄位標「待補」。
- 用繁體中文,語氣直接。

## 工作表輸出格式
```
# 〔專案名〕Double Diamond 工作表
## Discover:受影響的人 / 訪談與觀察計畫 / 已有洞察
## Define:挑戰句 / 三項檢查結果
## Develop:選項 A / B / C / 靈感來源 / 共創對象(含接收方)
## Deliver:選定選項 / 測試設計 / 成功標準 / 失敗時的下一步
## 來源標註:本表哪些是原文、哪些是補充
```
